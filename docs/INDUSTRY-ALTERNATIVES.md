# 行业常见替代方案：条件式比较

没有“永远最先进”的架构，只有与约束匹配的方案。下表中的团队规模是经验范围，不是硬门槛。

## 1. 存储

| 方案 | 复杂度 | 可靠性/扩展性 | 部署成本 | 适用场景 | 何时从 Tempo 方案切换 |
| --- | --- | --- | --- | --- | --- |
| 原子 JSON | 低 | 单进程可靠；查询/并发弱 | 几乎为零 | 个人工具、少量记录 | 数万历史、复杂过滤、多进程写 |
| SQLite | 中低 | ACID、索引、单机很强 | 一个文件 | 桌面应用、小团队本地服务 | Tempo 最自然的下一步 |
| PostgreSQL | 中高 | 多用户并发、备份与权限成熟 | 需要服务运维 | Web SaaS、多实例 | 远程部署、多用户、横向扩容 |
| 事件溯源 | 高 | 完整审计/回放，读模型复杂 | 基础设施与认知成本高 | 金融、审计、复杂领域 | 必须重建任意历史状态时 |

事件溯源不是“更好的日志”；它要求事件成为事实源并设计版本兼容。Tempo 当前没有这个需求。

## 2. 计时运行位置

| 方案 | 优点 | 风险 | 适用 |
| --- | --- | --- | --- |
| 浏览器计时 | 最少代码 | 标签关闭/节流/多标签竞争 | 教学 demo、临时倒计时 |
| Express 后台 | 状态唯一、可复用现有服务 | 进程停机时不能主动通知 | Tempo 这种本地 Web 应用 |
| Service Worker | 可做部分后台工作 | 生命周期由浏览器决定，精确定时不保证 | PWA 缓存、推送协作 |
| Tauri/Electron 原生进程 | 托盘、通知、系统集成强 | 打包、签名、升级成本 | 产品化桌面应用 |

## 3. 实时通信

| 方案 | 复杂度 | 特点 | 适用 |
| --- | --- | --- | --- |
| REST 轮询 | 低 | 调试简单，有固定延迟 | 状态小、几秒延迟可接受；Tempo 当前方案 |
| SSE | 中 | 服务端单向推送，自动重连 | 进度、通知、监控流 |
| WebSocket | 中高 | 双向长连接 | 协作编辑、实时控制、高频事件 |

番茄只需每几秒校准，WebSocket 的连接管理收益有限。若未来同时推送通知、实时 ActivityWatch 流和多客户端控制，可评估 SSE/WS。

## 4. 前端状态

| 方案 | 解决的问题 | 不应承担 |
| --- | --- | --- |
| TanStack Query | 服务端数据缓存、失效、重试 | 本地表单每个按键 |
| Redux/Zustand | 复杂客户端共享状态 | 自动替代 API cache 设计 |
| 直接 fetch | 最透明、依赖少 | 大量重复 loading/error/cache 代码 |

Tempo 把表单草稿留在 `useState`，把服务端事实交给 Query。若出现复杂离线编辑、撤销栈或画布交互，Zustand/Redux 才更有价值。

## 5. 应用形态

| 方案 | 复杂度 | 部署 | 团队/场景 |
| --- | --- | --- | --- |
| 模块化单体 | 中低 | 一个服务 | 1–10 人、领域仍紧密；Tempo |
| 全栈框架 | 中 | 路由/渲染/部署约定统一 | Web 产品、SSR、团队约定 |
| 微服务 | 高 | 每服务独立但需观测/网络治理 | 多团队、独立扩缩与发布边界 |

微服务不是把文件夹变成端口。只有组织和部署边界真的独立时，它的成本才可能值得。

## 6. 后台任务

| 方案 | 可靠性 | 适用 |
| --- | --- | --- |
| 进程内 timer | 进程活着时可靠；重启需 reconcile | 本地轻任务；Tempo 自动完成检查 |
| 系统计划任务 | 跨应用启动可靠，细粒度业务状态不便 | 启动 Tempo、每日维护 |
| Redis/云任务队列 | 重试、并发、可观测性强 | 分布式耗时任务、多 worker |

## 7. Migration

JSON schema migration 适合少量整体文档，可用纯函数测试。数据库 migration 适合表、索引、大数据增量更新并由工具记录已执行版本。若 Tempo 换 SQLite，应把 v3 JSON 作为一次 import source，而不是继续在运行时维护两套事实源。

## 8. 测试组合

| 层 | 快速性 | 发现的问题 | Tempo 用法 |
| --- | --- | --- | --- |
| 单元 | 最快 | DST、区间、状态机边界 | 纯函数与 Service |
| API | 中 | schema、状态码、层连接 | Supertest + mock ActivityWatch |
| E2E | 慢 | 页面、导航、真实交互 | Playwright 桌面/平板 |
| 完整集成环境 | 最慢/最真实 | 真实 watcher/系统差异 | 发布前本机 smoke test |

全靠 E2E 会慢且难定位；全靠单元测试会错过装配错误。小项目也不需要追求测试金字塔的固定比例，应该按风险放测试。
